# Plan I 第二刀：先封严 SQLite-first，再进入团队 PK 入库

## Goal

把计划 I 从“最近同步记录 SQLite-first”推进到一个更稳的闭环：

- 先修正 SQLite-first 的边界语义，确保数据库可用但角色筛选为空时不会误走 OSS fallback。
- 让深色主界面与异位面后台展示保持一致，尤其是最近同步记录、最近后台动作、协作数据库状态与数据来源提示。
- 完成后再进入下一阶段：`pk_latest` 迁入 SQLite，让团队 PK / 团队对齐分逐步摆脱 OSS JSON 索引。

## Current Context

已提交：

- `0cc5470 feat: read recent uploads from sqlite`
- `collab_db.py` 已新增 `recent_uploads()`
- `/api/collab/uploads/recent` 已改为 SQLite 优先、OSS 兜底
- `temu-dashboard.html` 的最近同步/审计已改成紧凑日志
- 深色主界面的协作数据库空库状态已改为 warn

前端分支只读复核指出：

- `temu-dashboard-editorial.html` 仍未同步紧凑日志样式
- 异位面的协作数据库空库状态仍可能误导为 ok
- 异位面后台概览副标题仍是旧口径
- 前端未展示 `/api/collab/uploads/recent` 返回的 `source=sqlite|oss`

后端分支只读复核指出：

- DB 可用但当前角色过滤后为空时，现逻辑会继续 fallback 到 OSS
- 当前先查全局最近 100 条再按角色过滤，后续数据多时主管可能漏本组旧记录
- OSS fallback 仍依赖 `pk_latest` 补字段，历史语义和 SQLite 固化记录不同

## Proposed Approach

下一步不要直接迁 `pk_latest`。先做一次“闭环封口”：

1. 后端把 `recent_uploads` 查询条件下推到 SQLite。
2. API 区分“DB 正常但无可见记录”和“DB 异常才 fallback OSS”。
3. 前端两个界面都显示数据来源：`SQLite 索引` 或 `OSS 兜底`。
4. 异位面同步主界面的后台日志密度与数据库状态口径。
5. 验证通过并提交后，再启动 `pk_latest` 入库计划。
