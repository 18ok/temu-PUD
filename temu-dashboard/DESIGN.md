# 跨境经营诊断系统 — Design Register

> 内部数据工具 · 非 marketing · 多平台经营诊断 · 团队协作下的个人成长

## Product

- **用户**：跨境运营同事、组长、主管、老板
- **任务**：导入平台经营数据 -> 商品诊断 -> 亏损品池 / 爆品复盘 -> 团队规则沉淀
- **平台**：Temu 先行，SHEIN / 淘宝天猫作为后续平台适配器；公司经营总览在平台子系统之上汇总组长与小组成绩
- **成功标准**：系统能回答“为什么爆、为什么亏、下一步怎么做、经验如何沉淀”

## Product Position

产品本体不再是 `Temu 团队看板`，而是：

`跨境经营诊断系统`

当前落地形态是 `跨境经营诊断系统 · Temu 子系统`。Temu 是试点子系统，不是公司主系统本体；Temu / SHEIN / 淘宝天猫都是平台适配器，不是产品边界。

SHEIN 当前不是公司绑定分支，而是个人可迁移架构下的分项目：可以处理公司授权数据，但公司数据必须停留在运行时数据层，不能写死进代码、模板、算法、仓库或密钥配置里。

## Data Philosophy

系统不追求一开始就全自动，而是先把团队数据语言定准：

`平台原始表 -> 平台适配器 -> 统一经营模型 -> 诊断/复盘/规则`

现有 Temu 双 Excel 不废弃，降级为 `Temu 适配器`。新版经营诊断模板用于承载更深的业务因果：

- 商品基础
- 每日表现
- 运营动作
- 问题诊断
- 规则沉淀
- 亏损品池
- 爆品复盘

数据主权原则：

- 代码、字段模型、适配器、模板、诊断逻辑属于可迁移的个人架构资产。
- 公司真实数据属于运行时输入和客户/项目数据，不属于代码资产。
- 任意公司数据必须能按 `project_id` / `workspace_id` / `company_id` 清理，不影响系统继续处理下一套数据。
- 数据库、OSS、本地缓存、日志都不能依赖单一公司的硬编码名称、账号或目录。
- 离职或切换项目时，应该删除数据与密钥，保留架构、空模板、通用规则和脱敏样例。

## UI Register

**Product UI**，不是 landing page。

- 左侧固定导航是系统骨架，必须第一眼看清结构。
- 管理后台独立入口，承载同步、配置、日志、权限等后台动作。
- 侧栏信息架构分三级：`公司经营总览` 放首位；`平台子系统` 折叠区包含 Temu / SHEIN / 淘宝天猫；当前 8 个业务页归入 `Temu 子系统功能` 二级导航。
- 模板下载不作为主入口；模板属于各系统内部的数据导入/配置能力。
- 深色主界面用于高频经营操作；浅色异位面用于长时间阅读、规则复盘和外部演示。

## Tokens

当前视觉方向继续克制：

- 深色底：`#0f0f17` / `#101319`
- 卡片：`#1a1a26`
- 强调金：`#e2b87a`，只用于选中、主操作、细线强调
- 正文：`#e8e6e3`
- 浅色异位面：纸白、墨色、低饱和金 / 蓝灰

## Motion

- 过渡 150-250ms
- 仅用于 hover、切页、toast、轻量状态反馈
- 禁止弹跳、翻转、Awwwards 式演出
- `prefers-reduced-motion: reduce` 必须降级

## Platform Templates

当前模板资产：

- `docs/templates/Temu商品经营诊断模板V1.xlsx`
- `docs/templates/SHEIN商品经营诊断模板V1.xlsx`

模板边界：

- Temu 模板承接当前团队真实经营链路，优先保持稳定。
- SHEIN 模板可以承载公司授权数据，但必须作为可删除的数据输入，不得把公司信息写死为系统默认值。
- SHEIN 模板先验证供货履约、平台扣费、退货、样品测试、机会假设和贡献利润模型。

下一步导入逻辑要从“只识别 Temu 双表”升级为：

- `platform`
- `source_file_type`
- `adapter`
- `normalized_product_id`
- `source_platform_fields`

## Do Not

- 不把 Temu 继续当成产品本体。
- 不把 OSS 当数据库。
- 不把 UI 卡片数量当产品价值。
- 不在没有运营动作表的情况下假装能解释因果。
- 不把团队对齐分做成简单排名和淘汰工具。
- 不把图片塞进 Excel；图片先用 URL，后续由 OSS 缓存。
- 不把任何公司的真实数据、账号、密钥、供应商报价写进代码仓库。
- 不设计删除公司数据后系统就不能运行的架构。
