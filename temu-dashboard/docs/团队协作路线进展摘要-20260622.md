> 用途：统一“团队下的个人成长”路线；不替代组员操作说明

---

## 一句话

在老板定的“数据上阿里云”路线下，当前仓库已经跑通了协作能力骨架：

- 前端：`temu-dashboard.html`
- 后端：`api_server.py`
- 能力范围：协作注册 / 登录、邀请码、小组、摘要上传 OSS、主管查看团队 PK

这条线不应被隐藏成“以后再说”的支线。正确定位是：**团队协作是主产品方向，个人 PK 是团队体系里的个人成长入口**。

---

## 现在怎么分阶段

### 阶段 1：个人 PK + 团队摘要同步

- 主入口：GitHub Pages
- 主价值：双 Excel -> 个人 PK / 诊断
- 团队价值：OSS 摘要同步、团队基准拉取
- 定位：每个人先在团队基准里看自己的差距和改进方向

### 阶段 2：身份 + 分组 + 主管团队 PK

- 入口：本地 `api_server.py`，或后续 ECS / 受控部署
- 能力：`/api/collab/*`
- 对象：主管、组长、组员
- 目的：验证“注册 -> 同步 -> 主管看团队 PK”链路，并把个人改进放入小组协作

---

## 已有技术事实

- 协作索引存 OSS JSON，不是 PostgreSQL
- 原始 Excel 仍只留本地，不上云
- 组织模型暂为单部门、四个小组
- 邀请码分 operator / supervisor / admin 三类
- `local_server.py` 现在只是转调 `api_server.py`

这些都说明协作线已经不是纯想法，而是“骨架已落地、需要按阶段放大”。

---

## 当前边界

- 团队协作是主线，但不要跳过个人 PK 和摘要同步的稳定阶段
- 不新增 PostgreSQL、SSO、多部门模型、爬虫市场库
- ECS 部署是放大协作范围的前置条件，不是个人 PK 使用的前置条件
- 版本和文案口径后续需要统一，避免同一版号里把“阶段 1”和“阶段 2”讲成互相矛盾

---

## 下一步建议

1. 先继续收口阶段 1：Pages / 本地双入口、个人 PK、团队摘要同步、版本文案。
2. 再推进 ECS，把协作能力从 localhost 扩成小范围团队试跑。
3. 若扩大内测，验收标准只看这条链：
   注册 -> 登录 -> 上传摘要 -> 主管查看团队 PK。
4. 老板确认编制前，不推进爬虫、市场库、完整数据库化改造。
