# 后端病灶体检 - 2026-06-23

## 一句话诊断

`api_server.py` 已经从“本地 OSS 代理”演变为“静态文件服务 + OSS Key 托管 + 协作账号 + 团队 PK API”的单文件轻后端；短期还能跑，但不能继续把新后台能力直接塞进 `TemuHandler`。

## 主要病灶

1. `TemuHandler` 承担过多职责
   - 位置：`api_server.py:551`
   - 现状：同一个类里处理静态文件、`/api/status`、`/api/sync`、`/api/collab/*`、旧 OSS 代理。
   - 风险：后续再加用户管理、邀请管理、同步日志，会让路由判断和错误处理越来越难改。

2. `/api/sync` 是兼容接口，不适合继续扩成后台 API
   - 位置：`api_server.py:684`
   - 现状：一个 action 分发 `write-env/ping/put/get`，同时承载 Key 迁移、OSS 读写和协作 bootstrap。
   - 风险：前端后台如果继续依赖 action 字符串，会越来越难判断失败来源。

3. 协作数据模型和 OSS 读写强耦合
   - 位置：`api_server.py:263`、`api_server.py:378`、`api_server.py:447`
   - 现状：注册、登录、上传、PK 榜全部直接读写 OSS JSON。
   - 风险：一旦要换数据库或加权限审计，需要拆很多函数。

4. 初始化容易把“服务可用”和“OSS 可用”混在一起
   - 位置：`api_server.py:822`
   - 现状：已改为后台线程初始化协作数据，避免阻塞启动，这是正确方向。
   - 风险：后续接口如果每次都 `ensure_collab_bootstrap()`，OSS 抖动仍会影响协作 API 响应。

5. `local_server.py` 已退化为兼容入口
   - 位置：`local_server.py:1`
   - 现状：只转发到 `api_server.main()`。
   - 风险：不大，但文档和启动脚本应逐步统一称呼，避免继续维护两个“后端入口”的错觉。

## 已做的止血治理

- 新增只读健康接口：`GET /api/status`
- 位置：`api_server.py:31`、`api_server.py:550`、`api_server.py:597`
- 特点：只读本地配置，不访问 OSS 网络，适合管理后台快速判断服务、OSS 配置、协作 API 开关和路由能力。
- 新增最近同步记录接口：`GET /api/collab/uploads/recent?limit=20`
- 位置：`api_server.py:502`、`api_server.py:716`
- 特点：读取 `upload_log.json`，按角色过滤；运营只看自己，主管看本组，管理员看全部。

## 下一步最小治理方案

先不拆文件，先拆边界：

1. 新增只读后台状态接口
   - `/api/status` 已完成。
   - `/api/collab/uploads/recent` 已完成。
   - 后续补 `/api/oss/status`、`/api/collab/users`、`/api/collab/invites`。

2. 保持旧接口兼容
   - 不删除 `/api/sync`。
   - 不删除 `local_server.py`。
   - 不改变前端现有上传/拉取/登录函数。

3. 等状态接口稳定后，再考虑物理拆文件
   - `oss_store.py`：OSS 签名、读写 JSON。
   - `collab_service.py`：注册、登录、上传、团队 PK。
   - `api_server.py`：只保留 HTTP 分发。

## 暂时不要动

- 不要现在引入 PostgreSQL、Redis、FastAPI、登录中间件。
- 不要马上删除旧 OSS 代理 `__temu_oss__`。
- 不要把协作 API 直接升格成公开版默认承诺。
- 不要一次性重构前端单文件和后端单文件，容易双线同时失稳。
