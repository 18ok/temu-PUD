# 平台化模板路线 V1

## 结论

不建议直接废弃现有 Temu 双表链路。

更稳的做法是：

- 现有两份 Temu 表格降级为 `Temu 适配器`
- 新增统一的 `跨境经营诊断模板`
- Temu / SHEIN 各自有一套平台模板
- 系统内部统一转成同一套商品经营诊断模型
- SHEIN 分项目先作为个人架构下的可插拔分项目推进，公司数据可以进入运行时，但不能绑定代码架构

也就是：

`平台原始表 -> 平台适配器 -> 统一经营模型 -> 亏损品池 / 爆品复盘 / 规则沉淀`

## 为什么不能马上摈弃旧双表

旧双表虽然业务深度不够，但有三个价值：

- 已经跑通导入、解析、团队对齐分、OSS 同步
- 能提供 Temu 当前真实经营数据入口
- 可以作为新模型的迁移对照组

如果立刻废掉，风险是：

- 当前可用链路断掉
- 新模板还没被团队真实填写验证
- 业务判断和代码同时大改，出问题难定位

所以旧双表应该变成历史兼容入口，而不是系统的未来上限。

## 产品命名

当前系统不应再叫 `Temu 团队看板`。

建议统一为：

`跨境经营诊断系统`

定位：

- 多平台
- 多店铺
- 团队协作
- 商品经营诊断
- 爆品复盘
- 亏损品池
- 规则沉淀

Temu / SHEIN 是平台适配层，不是产品本体。

## 看板入口设计

侧栏品牌区下方放系统访问入口，而不是模板下载入口：

- `Temu 系统`
- `SHEIN 系统`

入口用于打开两套系统。Temu 当前指向现有看板；SHEIN 在分项目窗口成立前显示 `待配置`。

模板下载不放在主入口里。模板属于每个系统内部的数据导入能力，后续可以放在导入页、管理后台或对应系统的配置区。

用户逻辑：

- 做 Temu：从主入口进入 Temu 系统
- 做 SHEIN：从主入口进入 SHEIN 系统；如果 URL 缺失，显示待配置占位
- 系统内部仍按统一字段做诊断

## 模板文件

当前已放置：

- `docs/templates/Temu商品经营诊断模板V1.xlsx`
- `docs/templates/SHEIN商品经营诊断模板V1.xlsx`

说明：

- Temu V1 兼容现有利润统计 / 店铺数据路径
- SHEIN V1 是独立平台模板，可以接公司授权数据，但公司店铺、订单、供应商、成本表等只能作为可删除输入存在
- SHEIN V1 已补充供货模式、样品状态、履约周期、平台活动、佣金/扣费、退货、库存周转、机会假设、样品复盘等字段

SHEIN 的商业验证顺序是：

1. 先用公开资料、竞品观察、模拟成本和样品测试记录验证品类逻辑。
2. 再沉淀适合 SHEIN 的字段、阈值和亏损原因分类。
3. 当公司数据进入时，先落到独立 `workspace/company/project` 数据层，验证清理、导出、备份和脱敏机制。
4. 架构资产始终保持通用：删除公司数据后，系统仍能用空模板、模拟数据或下一家公司数据继续运行。

## 后续平台适配器方向

### Temu 适配器

输入：

- 店铺利润统计 `.xls`
- 店铺数据记录 `.xlsx`
- 后续新经营诊断模板

输出统一字段：

- 商品基础
- 每日表现
- 运营动作
- 问题诊断
- 亏损品池
- 爆品复盘

### SHEIN 适配器

输入：

- SHEIN 经营诊断模板
- 公开竞品观察记录
- 脱敏样品测试记录
- 经权限确认后的 SHEIN 商品表现表 / 订单 / 履约 / 结算表

需要补充重点：

- 供货模式
- 样品测试结论
- 履约周期
- 退供 / 退货
- 平台活动
- 扣费结构
- 库存周转
- 供应链稳定性
- 贡献利润
- 机会假设

边界：

- 不直接读取与当前项目无关的公司数据。
- 不把 SHEIN 数据写入 Temu 团队 PK 主链路，除非显式选择同一 `workspace_id`。
- 不把真实供应商、真实账号、真实客户、真实订单明细提交进 Git 仓库。
- 不在代码里硬编码公司名、店铺名、账号、OSS Key、供应商报价。
- 不设计“删除某家公司数据后系统无法启动”的依赖。

## 技术落点

前端：

- 品牌名改为 `跨境经营诊断系统`
- 侧栏品牌区下方放系统入口折叠区：`Temu 系统` / `SHEIN 系统`
- 后续导入页增加平台选择：`Temu / SHEIN / 通用模板`

后端：

- 不按平台拆数据库主表
- 按统一经营模型建表
- 平台差异放到 adapter 层和扩展字段

数据库：

- `platform`
- `workspace_id`
- `company_id`
- `project_id`
- `data_sensitivity`
- `source_file_type`
- `source_platform_fields`
- `normalized_product_id`
- `spu_id`
- `sku_id`

这样既能兼容不同平台，又不会每个平台做一套孤岛系统。
