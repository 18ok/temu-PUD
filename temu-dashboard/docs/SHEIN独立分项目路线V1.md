# SHEIN 可插拔分项目路线 V1

## 一句话定义

SHEIN 分项目不是某家公司数据的复制分支，而是个人可迁移架构下的可插拔平台项目：可以处理公司授权数据，但公司数据只作为运行时输入存在，删除后不影响代码、模板、算法和系统架构继续使用。

## 为什么要独立

SHEIN 和 Temu 的经营问题相似，但不能把某家公司数据和个人架构资产混在一起。Temu 当前有团队协作、店铺数据和对齐分链路，适合继续收口真实运营能力；SHEIN 可以接真实业务数据，但必须按公司/项目/平台隔离。

可插拔的好处：

- 降低资产混同风险：代码、模板、字段模型、规则引擎属于个人通用架构，公司数据属于可删除输入。
- 可以处理公司真实店铺、订单、供应商、成本表，但必须进入隔离数据层，不能进入 Git 和代码默认配置。
- 避免把 SHEIN 数据误写进 Temu 团队对齐分，除非显式选择同一工作区。
- 可以大胆试字段、试模型、试品类，不污染主系统稳定性。
- 离职或切换项目时，删除数据、密钥和公司配置，系统仍能用空模板、模拟数据或下一套公司数据继续运行。

## 外部参考结论

基于 2026-06-24 的公开资料核查，SHEIN 路线需要重点关注这些事实：

- SHEIN 官方卖家页强调从申请、上架、发货到回款的完整卖家流程，说明它不是单纯选品工具，而是完整履约型 marketplace。
- SHEIN 官方商品上架页要求商品图片、标题、描述、品牌、货号、视频、类目属性等信息，说明商品内容完整度会直接影响上架和转化。
- SHEIN 官方退货政策提到订单送达后 30 天内可申请退货/退款，说明退货率和售后成本必须进入利润模型。
- SHEIN 官方 SFS 页面把仓储、打包、发货、退货作为可选履约服务，说明履约方式会影响成本、时效和风险。
- 行业资料普遍把 SHEIN 成本拆成佣金、履约/仓储、迟发/时效、库存周转和视觉内容优化，说明我们不能只看销售额和 ROAS。

## 数据边界

允许进入 SHEIN 分项目的数据：

- 公开页面观察结果
- 模拟成本
- 脱敏样品测试记录
- 公开竞品链接
- 人工整理的平台规则摘要
- 非敏感图片 URL
- 估算佣金、履约、退货、折扣成本
- 经公司授权导出的店铺、订单、履约、结算、成本、供应商数据
- 经权限确认后的内部图片 URL、商品链接、运营动作记录

不允许进入代码仓库或架构默认值的数据：

- 公司真实订单明细
- 公司真实供应商报价单
- 公司真实店铺账号、Key、Cookie、Token
- 公司真实客户信息
- 未脱敏的真实结算表
- 未授权的内部经营报表
- 公司专属目录、OSS Bucket Key、数据库密码、登录凭证

允许和禁止的核心区别：

- 允许：公司数据作为运行时输入进入本地数据库、受控 OSS 或本地缓存。
- 禁止：公司数据作为代码、模板默认值、测试样例、提交文件、算法常量或公开文档存在。

## 可剥离架构要求

SHEIN 分项目必须满足这些技术要求：

- 每条真实数据都必须带 `workspace_id`、`company_id`、`project_id`、`platform`、`data_sensitivity`。
- 本地缓存必须能按 `company_id/project_id` 清理。
- SQLite / 后续数据库必须支持按 `workspace_id/company_id/project_id` 导出和删除。
- OSS 对象路径必须带项目隔离前缀，例如 `workspaces/{workspace_id}/companies/{company_id}/projects/{project_id}/...`。
- 日志里不能写账号、Key、Cookie、客户信息和完整供应商报价。
- Git 仓库只保留空模板、通用字段、脱敏样例和算法，不保留公司真实数据。
- 删除某家公司数据后，系统仍能启动、导入新模板、跑模拟样例。

## 模板字段方向

SHEIN 模板已经从“Temu 改名版”调整为独立平台模板，核心 Sheet 包括：

- `01_SHEIN商品基础`：记录平台类目、供货模式、样品状态、目标供货价、履约成本、佣金假设、最小起订量、库存周期。
- `02_SHEIN表现记录`：记录曝光、点击、收藏、加购、订单、GMV、折扣成本、退货率、履约周期、贡献利润。
- `03_供货履约动作`：记录报价、打样、发货、补货、停供、换供应商等动作。
- `04_风险诊断`：记录侵权、尺码、材质、履约、退货、视觉、价格等问题。
- `05_机会假设池`：记录为什么认为某个品有机会、证据是什么、验证方式是什么。
- `06_样品测试复盘`：记录样品结果、失败原因、是否进入小批量。

## 商业判断框架

### 爆品为什么好

一个 SHEIN 品爆了，不能只写“销量高”。至少要拆成：

- 需求：是趋势、季节、价格带、风格、类目缺口，还是平台推流？
- 内容：主图、模特图、详情、标题、属性是否比竞品更完整？
- 价格：是供货价低、履约成本低、活动价有空间，还是牺牲利润换销量？
- 履约：是否发货快、退货低、库存周转顺？
- 复购：是否有套装、变体、颜色尺码扩展空间？

### 差品为什么差

一个品差到贴钱，至少要判断：

- 产品本身：质量、尺码、材质、图片承诺和实物是否错位？
- 市场原因：趋势过去、竞争变强、平台活动挤压价格？
- 平台原因：规则、扣费、活动门槛、履约时效变化？
- 运营原因：定价错、图错、属性缺失、上架类目错、没有及时停损？
- 供应链原因：起订量高、补货慢、退货高、质量不稳？

## 阶段计划

### 阶段 1：字段和利润模型验证

目标：先用模拟、公开、脱敏或少量授权数据，把 SHEIN 模板字段跑顺。

验收：

- 能记录至少 20 个候选品。
- 每个候选品都有机会假设、风险判断和贡献利润估算。
- 不出现被写死进仓库的公司真实敏感数据。

### 阶段 2：样品测试闭环

目标：用小样品、小批量、低风险方式验证机会假设。

验收：

- 每个样品都有测试结论。
- 能区分“产品不行”“供应链不行”“平台不适合”“运营动作错误”。
- 形成第一版 SHEIN 亏损原因分类。

### 阶段 3：适配器与数据隔离设计

目标：把 SHEIN 字段映射到统一经营诊断模型，并保证公司数据可剥离。

验收：

- 输出 `platform = SHEIN`。
- 输出 `source_file_type = shein_template`。
- 输出 `workspace_id/company_id/project_id/data_sensitivity`。
- 默认不写入 Temu 团队 PK 主链路。
- 能生成独立的 SHEIN 商品诊断结果。
- 能按项目导出和删除 SHEIN 数据。

### 阶段 4：受控真实数据运行

目标：在商业模型和隔离机制站得住之后，允许引入授权真实数据。

验收：

- 明确权限、脱敏、备份和删除机制。
- 真实数据只进入受控项目数据层。
- 可随时删除该公司/项目数据，保留架构继续使用。

## 下一步实现建议

优先做三件事：

1. 保持 Temu 主链路稳定，不让 SHEIN 沙盒影响当前团队协作。
2. 让系统能识别 `SHEIN商品经营诊断模板V1.xlsx` 的 Sheet 和字段，但先只做本地解析。
3. 新增 `platform`、`source_file_type`、`data_sensitivity` 三个基础字段，为后续数据库隔离打底。
4. 继续补齐 `workspace_id`、`company_id`、`project_id`，为离职/切换项目时的数据剥离打底。

暂时不要做：

- 不接 SHEIN 店铺账号密钥进代码仓库。
- 不做 SHEIN 自动爬取后台。
- 不把 SHEIN 数据默认同步进 Temu 团队 PK。
- 不为了“多平台”提前拆一套复杂数据库。
