# 数据主权与可迁移架构原则 V1

## 一句话

系统可以处理公司数据，但系统架构必须是个人可迁移资产：公司数据可进入、可分析、可删除；代码、模板、字段模型、诊断算法和部署方式不能被某家公司绑定。

## 分层原则

### 个人架构资产

这些可以留在代码仓库里：

- 前端页面和 UI 结构
- 后端 API 和协作接口
- 数据库 schema
- 平台适配器
- 空模板
- 脱敏样例
- 通用字段模型
- 通用诊断规则
- 公式逻辑
- 文档中的方法论

### 公司运行时数据

这些可以被系统处理，但不能提交到仓库：

- 店铺真实订单
- 真实结算表
- 真实供应商报价
- 公司成本表
- 客户信息
- 店铺账号
- OSS Key / API Key / Cookie / Token
- 内部经营报表
- 未脱敏图片和商品链接

## 必须支持的剥离动作

系统后续要支持：

- 按 `company_id` 删除全部公司数据。
- 按 `project_id` 删除单个项目数据。
- 按 `platform` 导出或清理 Temu / SHEIN 数据。
- 清空本地缓存后，系统仍能正常打开。
- 清空 SQLite / 后续数据库后，系统仍能重新初始化。
- 删除 OSS 中某个公司前缀后，不影响其他公司或个人模板。
- 删除 `.env` 后，系统进入未配置状态，而不是崩溃。

## 字段要求

真实数据进入系统时，至少带这些元字段：

- `workspace_id`
- `company_id`
- `project_id`
- `platform`
- `source_file_type`
- `data_sensitivity`
- `created_at`
- `created_by`

推荐的 `data_sensitivity`：

- `sample`：模拟样例
- `public`：公开资料
- `desensitized`：脱敏数据
- `company_internal`：公司内部数据
- `secret`：密钥/账号/高敏数据，默认不入库、不入日志、不入 Git

## Git 红线

永远不要提交：

- 公司真实 Excel
- 真实账号截图
- API Key / Secret
- Cookie / Token
- `.env`
- 真实供应商报价
- 真实订单明细
- 包含客户信息的日志

## 架构验收标准

如果离职或切换项目，执行这些动作后系统仍应可用：

1. 删除公司数据目录。
2. 删除公司 OSS 前缀。
3. 删除 SQLite 中对应 `company_id/project_id` 数据。
4. 删除 `.env` 和本地密钥。
5. 用空模板或模拟数据重新启动系统。

如果做到这一步，说明我们带走的是“系统能力”，不是“公司数据”。
