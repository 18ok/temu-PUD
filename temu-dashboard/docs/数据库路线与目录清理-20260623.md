# 数据库路线与目录清理 - 2026-06-23

## 结论

项目已经到了“需要设计数据库边界”的阶段，但还不适合立刻把现有 OSS JSON 全量替换成数据库。

当前最稳的路线是：

1. 保留 GitHub Pages + 本地解析作为前端入口。
2. 保留 OSS 作为摘要文件与上传 JSON 的对象存储。
3. 新增数据库作为协作索引层，先承接账号、角色、权限、团队成员、上传记录、PK 最新索引、审计日志。
4. 等协作内测稳定后，再决定是否把更多业务指标从 OSS JSON 迁入数据库。

换句话说，数据库不负责替代 Excel 解析和所有文件存储，先负责解决团队协作的“秩序”和“可追踪”。

## 为什么现在不能只做外表

前端后台已经完成了导航、固定侧栏、后台入口、角色权限展示、危险动作确认。但如果继续扩协作能力，只靠 OSS JSON 会出现几个硬问题：

- 多人同时注册或上传时，`accounts_index.json`、`pk_latest.json`、`upload_log.json` 存在覆盖风险。
- 角色权限现在已有 `/api/collab/permissions`，但账号和权限仍落在 OSS JSON 文件里，后续管理会变重。
- 审计日志、清除确认、拉取团队基准这些动作需要可追踪记录，OSS JSON 不适合做查询和筛选。
- 主管看板、团队排名、最近同步记录会越来越像数据库查询，而不是文件读取。

## 推荐数据库范围

第一阶段只建协作索引库，不碰大文件：

- `users`：成员账号、显示名、小组、角色、状态、密码哈希。
- `groups`：小组信息。
- `invites`：邀请码、角色、使用次数、有效状态。
- `uploads`：每次同步摘要的用户、时间、OSS key、SPU 数、店铺记录数。
- `pk_latest`：每个成员最新对齐分与核心指标。
- `audit_logs`：登录、同步、拉取、清除、配置测试等后台动作。

继续放在 OSS 的内容：

- 每次上传的完整 JSON 摘要。
- 后续可能导出的周报、快照包、附件。

## 技术选择

内测本地优先：SQLite。

- 优点：零部署、Python 标准库自带、适合当前单机本地服务。
- 风险：多人跨机器共享时不够用。

ECS/正式协作：PostgreSQL。

- 优点：并发、权限、审计、查询都更稳。
- 风险：需要部署、备份、连接配置和运维。

建议先写数据库适配层：

- `db.py`：统一读写接口。
- `api_server.py`：只调用接口，不直接关心 SQLite/PostgreSQL。
- 初期实现 SQLite，后续可替换 PostgreSQL。

## 下一步实现目标草案

在不推翻现有 OSS 摘要同步的前提下，新增 SQLite 协作索引层，将账号、权限、最近上传、PK 最新索引和审计日志从 OSS JSON 文件读写中抽出；验证标准是 `/api/collab/permissions`、`/api/collab/uploads/recent`、登录注册和团队 PK 能通过数据库查询返回，OSS 仍只保存上传摘要文件。
